# GEN-070.1 — Contrato Canônico de Páginas Avançadas

## Status

**IMPLEMENTED / VALIDATED**

Este documento detalha o schema oficial introduzido pela GEN-070.1. O contrato é implementado em `sistema/advanced_pages.py`, com validação semântica complementar em `sistema/advanced_pages_semantics.py`, e será consumido progressivamente pelo Advanced Page Designer, Application Preview Studio e gerador/runtime.

## Fonte de verdade

A configuração persistida pertence a:

```text
estrutura_json["advanced_pages"]
```

Não existe banco paralelo, configuração específica de Preview ou configuração específica de runtime.

Fluxo obrigatório:

```text
Advanced Page Designer
        ↓
estrutura_json["advanced_pages"]
        ↓
normalize_advanced_pages_config()
        ↓
validate_advanced_pages_semantics()
        ↓
 ┌──────┼──────────────┐
 ▼      ▼              ▼
Designer Preview   Gerador/Runtime
```

## Envelope do contrato

```json
{
  "version": 1,
  "pages": []
}
```

`version` permite evolução explícita do schema. A versão inicial suportada é `1`.

## Page

Cada página possui identidade estável, rota declarativa, contexto, navegação, componentes e ações.

```json
{
  "id": "contrato_detail",
  "name": "Detalhe do Contrato",
  "slug": "contratos/detalhe",
  "enabled": true,
  "context": {},
  "navigation": {},
  "components": [],
  "actions": []
}
```

### Regras

- `id` é estável e não deve depender do nome visível;
- `slug` deve ser único entre páginas avançadas;
- IDs duplicados falham;
- slugs duplicados falham;
- uma página desabilitada continua no contrato, mas não deve ser publicada pelo runtime;
- o normalizador não cria IDs aleatórios nem silenciosamente renomeia identificadores.

## Context

O contexto define o que a página representa.

```json
{
  "kind": "record",
  "entity": "Contrato"
}
```

Tipos canônicos:

```text
none
record
collection
```

Semântica:

- `none`: página sem entidade principal;
- `record`: página operando sobre um registro de uma entidade;
- `collection`: página operando sobre uma coleção de uma entidade.

`record` e `collection` exigem `entity` explícita.

## Navigation

```json
{
  "visible": true,
  "label": "Contratos",
  "icon": "bi-file-earmark-text",
  "group": "Contratos",
  "order": 10
}
```

Essa configuração descreve a intenção de navegação da página. Ela não substitui RBAC. A visibilidade final no Preview/runtime ainda deve passar pelo enforcement de autorização aplicável.

## Component

```json
{
  "id": "resumo",
  "type": "record_detail",
  "title": "Dados principais",
  "layout": {
    "x": 0,
    "y": 1,
    "w": 8,
    "h": 2
  },
  "binding": {
    "kind": "entity",
    "ref": "Contrato",
    "field": ""
  },
  "action": "",
  "config": {}
}
```

Tipos iniciais suportados:

```text
title
text
separator
alert
metric
table
record_detail
field_summary
report
dashboard
button
link
form
workflow_action
```

A lista é deliberadamente restrita. Novos tipos devem entrar por mudança documentada de contrato, não por conteúdo arbitrário enviado pelo usuário.

## Layout

O layout usa grade canônica de 12 colunas.

```json
{
  "x": 0,
  "y": 0,
  "w": 6,
  "h": 1
}
```

Regras da versão 1:

- `x`: 0 a 11;
- `y`: 0 ou maior;
- `w`: 1 a 12;
- `h`: 1 a 100;
- `x + w` não pode ultrapassar 12;
- componentes não podem ocupar a mesma célula da grade.

A GEN-070.3 poderá adicionar um algoritmo visual de reposicionamento determinístico. O contrato canônico, porém, nunca aceita sobreposição silenciosa como estado válido.

## Binding

Binding liga um componente a uma capacidade já conhecida pelo DjangoForge.

```json
{
  "kind": "entity",
  "ref": "Contrato",
  "field": ""
}
```

Tipos iniciais:

```text
none
page_context
entity
field
crud
form
dashboard
report
workflow
```

Regras:

- todo binding que aponta para outro contrato exige referência explícita;
- `field` exige também o nome/referência do campo;
- `page_context` significa que o componente consome o contexto já resolvido da página;
- a GEN-070 não permite SQL, Python ou expressão executável arbitrária como binding.

O normalizador estrutural garante a forma do binding. A validação semântica cruza referências com os metadados reais fornecidos pelos demais Designers antes de considerar o contrato executável.

## Validação semântica

`validate_advanced_pages_semantics()` recebe explicitamente os catálogos necessários e não consulta banco, request, settings ou models por conta própria.

A primeira cobertura validada inclui:

- existência da entidade do contexto;
- existência de entidade em bindings e ações CRUD;
- existência do campo em binding `field`;
- existência de transição de workflow;
- existência de relatório referenciado;
- não mutação do contrato de entrada.

A regra arquitetural permanece:

> normalização estrutural descreve se o contrato tem forma válida; validação semântica descreve se suas referências existem no universo conhecido da aplicação.

## Action

Ações são declarativas e separadas dos componentes que as apresentam.

```json
{
  "id": "editar_contrato",
  "kind": "crud",
  "label": "Editar contrato",
  "target": {
    "entity": "Contrato",
    "operation": "update"
  }
}
```

Tipos iniciais:

```text
navigate
crud
workflow
report
```

### CRUD

Operações canônicas:

```text
list
view
create
update
delete
```

A ação referencia uma entidade e uma operação. Ela não cria permissão própria; o Permission Designer continua sendo responsável pela autorização.

### Workflow

```json
{
  "entity": "Contrato",
  "transition": "aprovar"
}
```

A página referencia a transição existente; não redefine estados ou transições.

### Report

```json
{
  "entity": "Contrato",
  "report": "contratos_vencendo"
}
```

A página referencia o ID estável do Report Designer.

### Navigate

```json
{
  "page": "contrato_workspace"
}
```

A página de destino deve existir no mesmo contrato normalizado.

## Component → Action

Um componente interativo pode apontar para uma ação por ID:

```json
{
  "id": "btn_editar",
  "type": "button",
  "action": "editar_contrato"
}
```

Se `action` estiver preenchido e o ID não existir em `page.actions`, o contrato é inválido.

Isso permite que apresentação e comportamento permaneçam desacoplados sem duplicar a definição da ação.

## Fail-closed

`normalize_advanced_pages_config(..., strict=True)` é a interpretação estrutural executável do contrato e `validate_advanced_pages_semantics()` valida as referências externas antes do consumo funcional.

Configurações inválidas provocam `AdvancedPageContractError` e não devem ganhar comportamento permissivo por fallback.

O modo `strict=False` existe para Designer/inspeção e pode descartar páginas inválidas, mas páginas descartadas não são consideradas executáveis.

Princípio:

> tolerância no Designer não significa tolerância no runtime.

## Erros estruturados

`AdvancedPageContractError` carrega:

```text
code
message
page_id
component_id
action_id
```

Isso permite que o futuro Page Designer associe um erro diretamente ao elemento visual responsável.

## Compatibilidade com Designers existentes

A fronteira oficial permanece:

```text
CRUD Designer       → define comportamento CRUD
Form Designer       → define formulário
Dashboard Designer  → define dashboard
Report Designer     → define relatório
Workflow Designer   → define processo/transições
Permission Designer → define autorização
Advanced Page       → compõe/referencia essas capacidades
```

Referenciar não significa copiar.

O contrato de página armazena IDs/referências suficientes para localizar a capacidade externa, mas não replica sua configuração interna.

## Exemplo completo

```json
{
  "version": 1,
  "pages": [
    {
      "id": "contrato_detail",
      "name": "Detalhe do Contrato",
      "slug": "contratos/detalhe",
      "enabled": true,
      "context": {
        "kind": "record",
        "entity": "Contrato"
      },
      "navigation": {
        "visible": true,
        "label": "Contrato",
        "icon": "bi-file-earmark-text",
        "group": "Contratos",
        "order": 10
      },
      "components": [
        {
          "id": "titulo",
          "type": "title",
          "title": "Resumo do contrato",
          "layout": {"x": 0, "y": 0, "w": 12, "h": 1},
          "binding": {"kind": "page_context", "ref": "", "field": ""},
          "action": "",
          "config": {}
        },
        {
          "id": "resumo",
          "type": "record_detail",
          "title": "Dados principais",
          "layout": {"x": 0, "y": 1, "w": 8, "h": 2},
          "binding": {"kind": "entity", "ref": "Contrato", "field": ""},
          "action": "",
          "config": {"fields": ["numero", "objeto"]}
        },
        {
          "id": "editar",
          "type": "button",
          "title": "Editar",
          "layout": {"x": 8, "y": 1, "w": 4, "h": 1},
          "binding": {"kind": "page_context", "ref": "", "field": ""},
          "action": "editar_contrato",
          "config": {}
        }
      ],
      "actions": [
        {
          "id": "editar_contrato",
          "kind": "crud",
          "label": "Editar contrato",
          "target": {
            "entity": "Contrato",
            "operation": "update"
          }
        }
      ]
    }
  ]
}
```

## Testes da GEN-070.1

Arquivos:

```text
sistema/test_advanced_pages_contract.py
sistema/test_advanced_pages_semantics.py
```

Cobertura validada:

- envelope versionado;
- página completa;
- IDs estáveis/duplicados;
- slug duplicado;
- contexto obrigatório;
- binding explícito;
- overflow da grade;
- colisão de layout;
- referência componente → ação;
- navegação para página inexistente;
- modo tolerante;
- cópia segura por `page_map()`;
- entidade de contexto inexistente;
- campo inexistente;
- entidade CRUD inexistente;
- transição de workflow inexistente;
- relatório inexistente;
- preservação imutável da entrada.
